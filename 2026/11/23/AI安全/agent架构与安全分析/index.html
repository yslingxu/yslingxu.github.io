agent架构与安全分析

发表于2026-11-23|更新于2026-11-24|AI安全
|浏览量:

1. Agent 基本架构

1.1. 整体流程

Agent 系统采用分层架构设计，主要流程如下：

1.2. 核心组件

1.2.1. 任务路由（Task Router）

  • 功能：LLM 进行任务复杂度判断
  • 职责：根据用户输入的复杂程度，将任务分发到不同的执行路径

1.2.2. 执行路径（三种模式）

  1. Direct 模式

    • 适用于简单直接的任务
    • 流程：LLM输出 → Memory提取 → Memory更新/合并 → 结束

  2. Single Agent 模式

    • 适用于中等复杂度的任务
    • 流程：单Agent调度 → Agent Loop → 输出

  3. Multi Agent 模式

    • 适用于复杂任务
    • 流程：LLM进行DAG任务规划 → Sub Agent调度 → Agent Loop → 输出

1.3. Agent Loop 核心机制

Agent Loop 是系统的执行核心，包含以下关键模块：

1.3.1. 执行模块

  • 外接 Tools/MCP：调用外部工具和 MCP（Model Context Protocol）服务
  • 外接 RAG：检索增强生成，访问知识库

1.3.2. 管理模块

  • Context 管理/压缩：
    • 位置：Agent Loop 内部、Direct 路径
    • 功能：优化上下文长度，提升性能

1.3.3. 安全模块

  • 权限及安全检查：验证操作的合法性
  • 人工介入审批：高风险操作需要人工确认

1.4. 记忆系统

  • Memory 提取：从历史交互中提取相关信息
  • Memory 更新/合并：整合新的交互结果，维护长期记忆

2. 安全问题一：数据泄露

2.1. 风险点识别

  1. LLM 输出
  2. 外接 Tools/MCP
  3. 外接 RAG
  4. 最终输出

2.2. 数据泄露场景

2.2.1. 场景 1：敏感信息直接输出

  • LLM 在处理过程中可能将敏感数据（密钥、个人信息）直接返回给用户

2.2.2. 场景 2：外部工具泄露

  • 调用外部Tools/MCP/RAG服务时，可能将内部数据/密钥传递到不可信的第三方
  • 可能调用超出用户权限范围的外部Tools/MCP/RAG
  • RAG检索系统可能返回超出用户权限范围的敏感文档

2.2.3. 场景 3：跨会话数据污染

  • 不同用户、Agent 或会话之间的数据未正确隔离

2.3. 防护措施

2.3.1. 密钥管理

  • 措施：工具密钥应由 Secret Manager 统一管理
  • 原则：避免硬编码，使用环境变量或密钥管理服务

2.3.2. 参数与内容检查

  • 传递参数检查：外接时对输入参数进行敏感内容过滤
  • 读取内容检查：对从外部获取的内容进行安全扫描

2.3.3. 身份与权限验证

  • 措施：外接时验证调用身份是否有权限访问目标资源
  • 原则：基于 RBAC（Role-Based Access Control）或 ABAC（Attribute-Based Access Control）

2.3.4. 输出安全检查

  • 措施：最终输出前进行敏感内容检测
  • 技术：使用 DLP（Data Loss Prevention）策略，检测并脱敏 PII、密钥等

2.3.5. 隔离机制

  • 会话隔离：不同用户会话之间数据完全隔离
  • Agent 隔离：Sub-Agent 之间的数据访问受限
  • 上下文隔离：确保 Context 不跨越权限边界

3. 安全问题二：提示词注入

3.1. 风险点识别

  1. 用户输入（直接提示词注入）
  2. 外接 Tools/MCP（间接提示词注入）
  3. 外接 RAG（间接提示词注入）

3.2. 提示词注入类型

3.2.1. 类型 1：直接提示词注入

  • 来源：用户输入
  • 示例：
  • 风险：恶意用户通过精心构造的输入，试图覆盖系统提示词

3.2.2. 类型 2：间接提示词注入

  • 来源：外接 Tools、MCP 服务、RAG 检索结果
  • 示例：
  • 风险：外部数据源被攻击者植入恶意指令，Agent 误将其视为系统指令执行

3.3. 防护措施

3.3.1. 提示词可信度标记

  • 措施：在提示词拼接时明确标注内容来源的可信度
  • 实现：

3.3.2. 工具调用安全检查

  • 身份验证：确认调用者身份
  • 权限检查：验证是否有权限执行操作
  • 安全审计：记录所有工具调用行为
  • 人工审批：高风险操作（如删除、转账）需人工确认

3.3.3. 最小权限原则

  • 工具权限限制：每个 Tool 只能访问必要的资源
  • 沙箱环境：在隔离环境中执行不可信代码
  • 白名单机制：只允许调用预定义的安全工具

3.3.4. 输入输出检查

  • 输入过滤：检测并过滤恶意指令模式
  • 输出验证：确保输出不违反安全策略
  • 异常检测：识别异常行为模式

3.3.5. 日志审计

  • 完整记录：记录所有输入、输出、工具调用
  • 异常告警：检测到可疑行为时及时告警
  • 事后分析：支持安全事件的回溯分析

4. 其他安全考虑

4.1. 供应链安全

  • 插件安全：验证第三方插件的可信度
  • 依赖库安全：定期更新依赖，扫描漏洞
  • MCP 服务安全：评估外部 MCP 服务提供商的安全性
  • 外部 Tool 安全：审查外部工具的权限和行为
  • 外部模型安全：防范模型幻觉、输出篡改

4.2. 预算安全

  • 无限循环防护：设置最大迭代次数
  • Token 限制：控制单次请求和总体 Token 消耗
  • 资源消耗监控：监控 CPU、内存、网络使用

4.3. 合规安全

  • 数据保护法规：遵守 GDPR、CCPA 等数据保护法规
  • 行业标准：符合特定行业的安全标准（如医疗 HIPAA、金融 PCI DSS）
  • 审计要求：满足合规审计的日志和追溯要求

5. 架构安全最佳实践

5.1. 纵深防御

  • 在每个架构层面都部署安全控制
  • 不依赖单一安全机制

5.2. 零信任原则

  • 假设所有输入都是不可信的
  • 持续验证身份和权限

5.3. 安全设计

  • 在架构设计阶段就考虑安全问题
  • 安全功能应是系统的核心组成部分，而非事后补丁

5.4. 持续监控

  • 实时监控系统行为
  • 建立安全事件响应机制

5.5. 定期评估

  • 定期进行安全评估和渗透测试
  • 根据新威胁更新安全策略

6. 总结

Agent 系统架构需要在功能性和安全性之间取得平衡。通过：

  1. 清晰的架构分层：Task Router、执行路径、Agent Loop
  2. 完善的安全机制：权限检查、敏感内容过滤、隔离机制
  3. 防范两大核心威胁：数据泄露和提示词注入
  4. 全方位的安全考虑：供应链、预算、合规

可以构建一个既强大又安全的 Agent 系统。

关键原则：安全不是一次性工作，而是需要持续关注和改进的过程。
